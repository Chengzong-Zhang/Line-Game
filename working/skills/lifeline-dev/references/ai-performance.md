# AI、攻防与性能

任务涉及 AI 选择、强度、防守、PASS、搜索或领土/渲染性能时读取。先分清规则修正、等效提速、策略变化和训练；用户说“不能减弱”时，不能用降低搜索预算达成延迟指标。

## 四档 AI 必须有实际区别

用户要求的产品方向是简单、中等、困难、终极四档，覆盖相应的 2–6 人场景。每档先核对实际运行路由、算法/模型、预算、适用人数/棋盘、数据来源和准入状态。

| 档位意图 | 实现与验收重点 |
| --- | --- |
| 简单 | 用户要求借鉴双人 Minimax/训练经验形成基础 AI；说明实际是搜索、蒸馏还是训练策略，不能只改标签 |
| 中等 | 复用当前已有小 AI 及其真实能力；作为对照/教师时绑定版本与适用范围 |
| 困难 | 针对多人复杂拓扑优化搜索、剪枝与响应；说明实际搜索/模型和同预算强度，不能悄悄降深度、缩候选冒充升级 |
| 终极 | 用户要求从双人效果最好的模型出发，结合 Minimax 与现有 AI 造数据、训练并验证多人能力；“最好”须有相应评估，不靠类名或标签确定 |

这是目标与验收方式，不宣称四档均已成熟。不同人数可能使用不同实现，UI/日志/manifest 如实体现。模型训练、导出、加载、数值验证、完整对局评估、产品准入和发布分开记录；`strength_verified=false`、`BUILT_NOT_VERIFIED` 等候选不能进入普通正式档位。旧测试因未准入而失败时修正测试适用范围或补评估，不放开门禁凑通过。

复用 `MultiplayerRuntime.js`、`ModelFreeAI.js`、`AIWorker.js`、当前模型 manifest 与 Worker 路由；新增文件、权重和 manifest 必须进入各端构建依赖。模型未加载、hash 不符或超时要保留棋局，展示真实错误/降级，不伪装成正常终极 AI。已有合适资产时不为界面接入重训。

## 防守、连续切断与进攻

用户指出的问题同时包括“被连续切断”和“不会制造对手难以化解的连续切断”；不能只降低进攻/领土权重，也不能只修三人某一档后宣称覆盖 2–6 人。

- 优先从真实棋谱定位动作前缀、规则、起点、行动顺序、AI 档位和预算，形成固定失败局面。合成例用于补边界，不能取代真实失败点。
- 检查己方节点/线覆盖损失、出生点连通、桥接结构、对手下一次实际行动及后续威胁；评估主动切断时保留对手合法反击，不把单步吃子当不可破解组合。
- 多人顺序按实际存活席位推进，不能把每个对手都当作立即行动或默认所有对手合作。说明 Minimax/Max-n/paranoid/对手模型等真实选择，不混用结论。
- 启发式调整先与当前版本在同局面/预算比较动作、损失、反击和终局；保留失败候选。局部防守改善不自动意味着总体胜率提升。
- 在隔离引擎完成完整历史/逻辑边的推演。异常、超时或未完成的局部比较不能提交不可靠候选或改变正在玩的棋。若保留原策略，记录 fallback 来源。
- 宣称“强制连续切断/不会被打破”须有该局面的完整合法回应证据；普通搜索/样例只能写发现了战术候选。覆盖人数、形状、起点和档位按实际结果列出。

相关入口见 `AIEngine.js`、`MultiplayerStandardDefense.js`；回归优先使用项目地图列出的 Minimax 防守与多人防守脚本，再扩展本次反例。

## PASS 是策略动作

“不会跳过”不只是在无合法落点时自动跳过。区分主动 PASS、被迫跳过、搜索失败/无结果、认输和终局。

- 搜索根节点、递归展开、模型动作映射、Worker 消息、UI/controller、联机日志、存档和重放使用一致的显式 PASS 语义；不能将 `null`/超时一律当 PASS。
- PASS 后按对应规则更新行动方、连续次数、完整历史和终局；终局使用离散 `area`/赢家，不能用启发式大分替代。
- 可复用的安全分支是：隔离模拟 PASS 立即终局且当前玩家为唯一胜者时选择它；仍须处理执行失败并保持对局。该分支只证明立即获胜 PASS，不等于一般策略 PASS 已解决。
- 覆盖有合法落点仍选择 PASS、非终局 PASS、连续 PASS 终局、平局/输局不可误判、终局不可续行、多人席位顺序、Worker 过期与页面实际执行。只通过一个 witness 不宣称全面掌握。
- 调用现有 `controller.skipTurn()` 等受控入口，失败保持棋局并明确状态；不要在 UI 绕过引擎伪造一次落子。

## 性能：保持效果，测量完整链路

先固定规则、棋盘/人数/起点、完整历史、局面前缀、模型/源码 hash、搜索深度与候选预算、随机种子、设备和冷热状态，再比较同条件结果。

分别量化输入反馈、排队/冷加载、计算、序列化/通信、几何生成、绘制与最终上屏。六名玩家顺序计算总时长、单步 AI 延迟、主线程阻塞和第一帧可见时间是不同指标。Worker 移走计算可以改善交互，但不自动缩短完整领土结果时间。

用户希望复杂局面尽量一秒内响应。这是目标；先明确目标设备、计时起止和验收判据。用户要求所有场景满足时，分位数不能替代硬上限；超时参数设为 1000ms、少数小盘均值或先画点线也不能证明“任何情况一秒内”。报告代表性大盘/多人/复杂历史的实测、尾延迟/最差例、超时与 fallback；确实仍超时就明确保留。

可优先探索的等效路径：

1. 候选共享、对称/等价归并、精确上下界和提前退出，减少生成后逐项重复检查。
2. 避免为“是否存在漏点”等布尔判断构造完整覆盖数组，复用邻接、缓冲区和安全的状态复制。
3. 依赖驱动的增量计算，只复用确认未受影响的结果。新连线可能改变远处封闭通道，不能仅重算落点附近或只凭颜色不变命中缓存。
4. Canvas 路径/图层与必要区域复用、去掉重复全盘绘制、合并调度；中间显示必须明确，不能把旧面积或近似填色当最终结果。
5. 减少 Worker 消息中的重复历史传输，在身份/摘要/版本校验下做增量；重开、悔棋、重连或摘要不匹配时安全恢复完整状态。

这是可选方向，不要求每次全部做。用户要求比较三种方法时给三种实测与最终选择；不把一次三方案要求变成所有小修复的固定流程。

规则/几何等效优化比较完整结果、状态与必要像素；纯搜索优化还要固定预算比较候选、分数和动作（等分动作遵守已声明的 tie-break）。有界样例一致只支持相应覆盖，不是一般数学证明。规则升级允许新旧规则结果不同，分别测试版本兼容，不能硬凑 v2/v3 输出一致。

长期性能批量、造数据、训练与棋力评估必须遵守 [研究与可靠运行](research-workflow.md)。实际测量前识别共享机器上的重任务，避免并发污染；不擅自暂停其他任务，不在测试里隐藏长自对弈。
