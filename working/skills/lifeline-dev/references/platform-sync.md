# 多平台同步与发布

仅在跨平台功能同步、迁移、构建、GitHub 同步或渠道发布时读取。“多平台同步”在本项目通常指源码、玩法、资源、构建与版本交付的一致性；账号云存档/跨设备进度是另一项产品能力，只有用户要求时才实现。

## 找到本次同步对象

下表为 2026-10-25 核对的定位线索。工作树前缀通常为 `C:/Users/zcz/.codex/worktrees/`，使用前查当前工件、`git worktree list`、状态、分支和远端；不要按目录名判断已完成或覆盖它。

| 目标 | 典型工作树/工程 | 同步边界 |
| --- | --- | --- |
| 网页与联机服务 | `C:/coding/py/line game`；`web/web前端/`、`web/web后端/` | JS 核心、UI、Worker、资源与服务协议分别纳入 |
| 微信小游戏 | `wechat-minigame/line game`；`wechat/minigame/` | 本工作树 Web 核心输入、原生 Canvas/API 适配、Worker、模型/指南分包；相关服务在 `wechat/` 下按当前入口定位 |
| Android / HarmonyOS | `lifeline-mobile/line game`；`mobile/` | 离线 Web 资源、Capacitor/原生桥、Android 与 Harmony 宿主、签名和升级链 |
| TapTap | `lifeline-taptap/line game`；`mobile/` | 复用 Android；渠道配置、真实 SDK/隐私/合规和商店流程 |

| Python 基础算法 | 主树及确实持有副本的平台树中的 `core algorithm/` | 对应规则实现、要求文档和独立固定例；不等于改动冻结研究环境 |
| GitHub | 当前配置的远端与目标分支 | 源码、测试、配置、文档和紧凑证据的版本交付；不是运行平台或部署收据 |

只修改本次要求的目标；对其余受影响端列缺口。“全部同步”应按实际能力覆盖所有相关目标，不能静默缩成只复制 Web；也不能借机新增平台、SDK、付费服务或云存档。

## 整合最完整的候选

1. **列功能覆盖，而非仅列文件。** 用户以 Web/Mini 为基准时核对两端后续修复，按两端已完成且可验证的产品能力取并集，不能缩成两端交集或旧统一包；平台不适用部分显式说明。 结合当前代码、未提交 diff、最近用户要求及对应聊天的结果，核对：规则/计分、2–6 人与棋盘/起点、AI 档位与攻防/PASS、领土性能、本地/联机悔棋、教程挑战、复盘/导入导出、存档恢复、中英文、好友房间和平台兼容。按任务删去无关项。
2. **选择来源并补差异。** 为每个目标端先列既有玩家能力与兼容行为的前后覆盖清单和回归（如挑战关卡、成绩/成就、本机档案、导出恢复、原生前后台和旧存档）。宿主适配不只包括编译配置；不能以采用新Web为由丢掉目标端独有成熟功能。 每项记录来源 checkout/commit 或未提交文件哈希、实际验证和目标缺口。最新时间戳不代表最完整；主树也可能缺少平台修复。语义整合共同核心，同时保留各端宿主、配置、登录、存储、签名和兼容修复。不要整目录覆盖，不从旧基线重做，不擅自搬走原改动。
3. **确认能交付的范围。** 已完成且验证通过的产品功能纳入统一候选；进行中的实验、未准入模型和未验证行为单列。若用户明确要求实验版本，做清楚标记的独立候选，仍不伪造正式准入。适配不了的能力给原因和可见提示，不悄悄降档或删入口。
4. **收齐依赖与资源。** 新的嵌套 `frozen-workers/`、顶层 `.mjs` 与动态 import 可能不被旧浅层复制脚本收录；先检查真实路由和完整递归依赖。 从实际入口追踪静态/动态 import、Worker/bundle、模型 manifest/权重、缓存版本、指南、Vue/MathJax/字体、许可、API/WS 地址和生成脚本。新增模块必须出现在目标依赖清单；改源码后重建相关 bundle 和 manifest，不能只复制旧 dist。
5. **按平台生成并验证。** dirty 主仓与旧宿主组合时优先在本机隔离候选中导出来源、叠加宿主；先读构建脚本的删除/覆盖范围，不能让 dist/renderer 清理作用于未授权原工作树。旧冻结清单要生成本次新清单，不得关闭校验。 在平台自己的构建路径执行，核对构建输入与产物哈希、版本和功能覆盖。核心同源不要求平台包字节相同；差异必须来自明确适配。继而做相关规则回归、实际入口交互和需要的跨端联机/恢复。
6. **冻结后交付。** 候选绑定来源、配置、依赖清单、产物哈希、测试命令/退出码与未验项。新增修改进入新候选并补受影响验证；不替换冻结内容、不改旧预期制造通过。上线前再次查当前候选覆盖，防止遗漏其他聊天刚完成的修复。

可在本次已有台账/收据中使用这张小表，无需为每次小修复创建完整发布系统：

| 功能 | 来源/哈希 | 目标平台与模式 | 已整合/差异 | 本次验证 | 交付状态/阻塞 |
| --- | --- | --- | --- | --- | --- |

同步完成的依据是上述行在所声明目标上的闭环。目标路径存在、两个文件同 hash 或旧测试全绿都不够。

## 复用现有构建入口

先读取目标 checkout 的 `package.json`、README 和脚本参数，确认输出位置及副作用。以下是当前入口示例，不是一键执行全部命令：

- 指南：`web/tools/sync-implementation-guides.mjs`，随后 `--check`；小游戏另核对 `src/guide-content.js` 及实际打包内容。
- 小游戏：在 `wechat/minigame/` 下，`npm run build`、`npm test`、`npm run release:prepare` / `release:verify`。构建会读取同工作树的 Web 模块，并校验模型分包来源。官方上传入口在 `wechat/ci/`，只在上传已授权时执行。
- 移动端：`mobile/tools/build-web.mjs`、`build-mobile.mjs`；当前清单与核验入口为 `config/current-web-sync-source-manifest.json`、`tools/current-web-sync-closure.mjs`、`tests/verify-current-web-sync-closure.mjs`。按本次版本生成清单，勿照搬带旧版本号的 npm 参数。
- Android 宿主使用现有 Capacitor/Gradle 流程；Harmony 使用现有 `mobile/tools/build-harmony-native.ps1` 等实际入口。Web 构建通过后仍需对应原生编译和包检查。
- TapTap 使用目标树的 `npm run build:taptap` / `verify:taptap`，沿用共享主线包名与签名，渠道差异留在适配层。
- 桌面、itch 和 iOS 从各自当前工程/发行目录读取构建入口，复用离线化脚本及资产清单。不要猜命令或把另一个工作树的 package scripts 当通用接口。

工具链不在 PATH 不等于没有安装：先读平台构建脚本与本机工具路径。Android/Harmony 使用实际宿主物理路径，注意 junction 字面比较与 PowerShell 版本；发现 JDK/SDK/Hvigor 仍须运行预检和实际编译才能宣称可构建。iOS 的 Web 资源准备不替代 macOS/Xcode。

## 平台必须补的验证

| 平台/链路 | 共用回归之外要验证 |
| --- | --- |
| Web | 真实 Canvas、点击/触摸、Worker、取消/重开/刷新；资源缓存、HTTP/WS 与实际服务版本 |
| 微信小游戏 | 无 DOM/BOM 的原生 API、当前 Worker 限制和队列、分包加载/体积、真机或云测、前后台恢复；保留旧 Android 正则兼容修复 |
| 跨端联机 | 同一房间的规则/设置、随机起点、动作顺序/去重、PASS/终局、悔棋投票、加入/断线/刷新恢复；客户端与服务共同验证 |
| Android / HarmonyOS | 原生构建、签名类型、安装、返回键/键盘、安全区域、前后台/进程回收、断网、文件导入导出、旧包覆盖升级与存档 |
| iOS | Windows 上资源检查不替代 Xcode archive、签名、iOS 运行和 TestFlight/App Store 状态 |
| Windows / Steam | 离线启动、Worker/模型/字体、完整对局、保存恢复；便携程序可玩不等于 Steam 上传、商店审核或公开 |
| itch.io | 相对路径和大小写、iframe/全屏、首次手势音频、存储拒绝、下载、实际 CDN 包和匿名访问；不能只测 localhost |
| TapTap | 按所选发行形式核实真实服务、权限/SDK 清单、隐私选择、认证/防沉迷、更新和实际下载安装；预约页不等于可玩分发 |

小游戏曾因旧 Android 无法解析静态 Unicode 属性正则而黑屏。相应修改要检查最终包而非只查源文件，在原失败设备类别复测；Node 成功不能证明黑屏消失。Worker 数量、分包限制、商店资质与政策会变，执行迁移/提交时查当前官方说明，不在技能中冻结数字。

## 统一发布，分别确认状态

- 同一服务器或渠道版本保持一个明确的发布执行者。发现其他聊天正在同步时，先只读比较目标、范围和候选差异；不要假设它已包含本任务，也不要平行激活另一个包。未经用户授权不向其他聊天发送工作指令。
- 在当前会话授权范围内持续完成 Git 提交/推送、服务器激活或官方上传。技能、旧聊天中的发布请求、旧脚本及可用凭据本身都不是本次外部动作授权。
- 部署前验证当前线上基线与候选，保留可回滚版本；沿用现有原子切换/恢复工具。不能为过门而删除基线校验或伪造 manifest，不替换生产数据库/用户存档。基线漂移先核实其来源，再生成合法的新发布方案。
- 登录需要用户时，先准备好候选和验证；复用有效的安全认证通道，避免反复打开一次性密码窗口。凭据只在用户本机受控入口输入，不进入聊天、仓库、日志或收据。
- SSH 中断或退出码异常后先读取本次持久收据、远端版本/哈希与健康状态，确认实际停在哪一步；按已有恢复路径继续，不能盲目重发。发布后查实际公开入口的引擎/资源、服务版本与代表性规则场景；HTTP 200 只证明可达。
- 微信开发版上传后，体验版指向哪个构建、体验权限、云测/真机、提审和公开分别核实；上传机器人中的新包不自动替换现有体验版。版本名称之外还要核对来源与包哈希。
- GitHub 已推送、Web 已激活、Mini 已上传、移动包已编译分别报告；单端成功不写“全部上线”。账号、设备、签名或资质阻塞只阻塞相应阶段，其余工程与材料继续完成。
- 渠道文案、图标、截图、录屏和隐私材料复用现有品牌并匹配最终版本。按用户看到的字段顺序给可复制内容和准确素材路径；不编造身份、权利、备案、签名、联系人或真实服务结果。新增付款、合同/独家条款及身份提交遵守本次明确授权。

收据尽量包含：目标平台、功能范围、规则版本、来源与候选 ID/哈希、构建/签名状态、实际环境、检查命令/退出码、交付入口、回滚位置、各阶段状态及最少剩余操作。使用项目既有状态定义；`PASS-CURRENT` 必须有本次对应证据，历史 PASS 不自动继承。
