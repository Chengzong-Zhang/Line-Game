# HarmonyOS native host

This is the native Stage-model ArkUI/ArkWeb host for the mobile web build. Run `npm --prefix mobile run build` to produce `mobile/dist`, copy the verified files into the ignored rawfile tree, and generate `entry/src/main/ets/generated/AssetManifest.ets` before opening the Harmony project in DevEco Studio.

The Web component loads only `https://lifeline.appassets.invalid/index.html`. Its request interceptor serves an exact generated asset allowlist from `resources/rawfile/web`; unlisted paths on that virtual origin receive 404, while requests to other origins are left to ArkWeb for the application's HTTPS/WSS backend calls. The reserved `.invalid` domain cannot collide with a production website. No `file:` URL or relaxed same-origin setting is used.

The native proxy limits storage operations to the shared bridge's single session key. Those operations are serialized, written through Preferences, flushed, and checked against the same Preferences instance before returning `{ flushed: true }`. A host API-shaped persistence model verifies save/read/clear behavior across two independent Preferences facades sharing a backing map; this models a new handle or process and is not evidence about Harmony's Preferences cache eviction or disk durability. A stored clear tombstone maps to `null` on load. Real cache eviction, crash durability, and cross-proxy races remain NOT-RUN. Replay sharing is a separate native operation and does not use the session key: the proxy writes a validated JSON replay into the app cache and opens the system share panel. A native `opened` or `dismissed` receipt does not prove that another app received or saved the replay. The JavaScript share Promise waits for confirmed panel dismissal; it rejects on a show failure or when closure remains unknown, and the UI must treat those outcomes as unconfirmed rather than successful delivery. The native open handshake is 30 seconds and the JavaScript handshake is 35 seconds. If opening remains unconfirmed, the native proxy reports unknown after a further 9 minutes and the JavaScript side has a 10-minute panel-close deadline. Unknown status keeps native sharing mutually exclusive and retains the active-file marker until an actual dismiss or a definite show rejection; the share Promise reports the unknown state to the caller.

The replay cache is bounded to 32 JSON files and 128 MiB. Files older than 24 hours are eligible for expiry cleanup; pressure-based eviction only reclaims unpinned files at least one hour old. Future-dated files are preserved when the system clock moves backward. `.active` markers survive process restarts and protect uncertain files from pressure eviction, while the 24-hour expiry can still remove an old marker and file after the original process is no longer actively sharing it. A file still active in the current process is not cleaned up. These cache rules cannot establish when the receiving app has finished reading a shared file.

Checkpoint E passed the revisioned session recovery and explicit-clear flow in the JavaScript integration harness, including removal of the legacy WebView clear marker and restart recovery. The host API-shaped Preferences facade model also passes save/read/clear, missing, malformed JSON, read/flush failure, and tombstone mapping checks. This is host evidence only: Harmony Preferences cache eviction, process-crash durability, and cross-proxy race behavior remain NOT-RUN and require SDK/device validation.

The mobile game footer opens a generated, self-contained HTML third-party notice at `legal/THIRD_PARTY_NOTICES.html`. It includes the full license text for all nine manifest entries, package versions and license identifiers, and a relative link back to `index.html`. The original Markdown notice and license text files remain bundled. The build receipt hashes the generator, inputs, and generated output.

The AppScope application icon and label, plus the EntryAbility icon, startup icon, label, and startup background, resolve to local Harmony resources. The current icon is a documented development placeholder generated from source; it is not final store branding. The placeholder generator is an explicit initialization tool that refuses to overwrite existing files, and ordinary builds preserve existing resources. HarmonyOS 5.0.0.71/API 12 compilation has now passed with the bundled Hvigor 5.8.9 toolchain and produced an unsigned HAP. This confirms local resource validation and ArkTS compilation, but not installation, runtime behavior, device acceptance, signing, or release readiness. The Android instrumentation source contains only an application-id smoke test; it has not been run on a device and is not native-feature verification.

For a reproducible local Windows build, use the bundled official Command Line Tools and JDK 21 with `mobile/tools/build-harmony-native.ps1`. The script calls the bundled Node and Hvigor 5.8.9 entry point directly. It does not run `hvigorw`, a package manager, or an online dependency install. Before compiling, it checks the selected Node/JDK/SDK, both project package declarations, the CLI and plugin versions, the CommonJS boundary file, and the two `@ohos` junction pairs under the project and `NODE_PATH`.

Run `-ValidateOnly` first to perform those checks without compiling. By default the script uses the toolchain already under `mobile/local_artifacts`; pass `-ToolRoot` and `-JavaHome` when using another installed tool bundle and JDK:

```powershell
$tools = 'mobile/local_artifacts/harmony-native-20261022-01/tools/command-line-tools'
$jdk = 'mobile/local_artifacts/native-build-20261022-parent01/temurin21/jdk-21.0.12.1+1'
$run = "mobile/local_artifacts/harmony-repro-$(Get-Date -Format yyyyMMdd-HHmmss)"
pwsh -NoProfile -File mobile/tools/build-harmony-native.ps1 -ToolRoot $tools -JavaHome $jdk -ValidateOnly
pwsh -NoProfile -File mobile/tools/build-harmony-native.ps1 -ToolRoot $tools -JavaHome $jdk -ArtifactDirectory $run -VerifyL26
```

Choose a new artifact directory for each build; the script refuses an existing directory. Hvigor runs from the Harmony project directory. The script requires both a zero exit code and an explicit `BUILD SUCCESSFUL` log entry before copying a HAP. It always passes `--no-incremental`, rebuilding the HAP after the current mobile Web receipt exists so the new HAP's modification time is later than that receipt and the existing verifier can bind it to the receipt's current packaged resources. It saves the full Hvigor log, exit code, copied unsigned HAP, SHA-256, and a compact build receipt containing the complete command there. `-VerifyL26` also runs `mobile/tools/verify-l26-harmony-hap.py` with a fresh verification directory. The script sets `DEVECO_NODE_HOME`, `NODE_HOME`, `DEVECO_SDK_HOME`, `JAVA_HOME`, `NODE_PATH`, and the Java/Node `PATH` entries only for its child build process, using isolated `HOME`, `USERPROFILE`, and `HVIGOR_USER_HOME` under the artifact directory; it restores the caller's process environment afterward. It does not write user-wide configuration. The HAP is unsigned, and this local build does not establish device runtime, formal signing, or store acceptance.

`npm --prefix mobile run prepare:harmony-release-signing` validates optional local signing input at `mobile/local_artifacts/release-signing/harmony-signing.json` or its documented environment variables and can generate an ignored Hvigor 5.8.9 build-profile overlay. The L27-B entry at `mobile/tools/harmony-release-build-entry.mjs` now consumes that overlay only inside a fresh isolated project under ignored `mobile/local_artifacts`; it never edits the tracked Harmony build profile. The entry requires a `FROZEN` release identity and the frozen Harmony certificate-chain SHA-256, runs Hvigor with isolated user/cache directories and `--no-incremental`, and then invokes the complete release-artifact verifier with the official `hap-sign-tool`. Hvigor may leave an unsigned intermediate beside the signed output. Acceptance requires exactly one strict `*-signed.hap`, exactly one metadata record with `isSigned: true` and the same `hapName`, and successful identity, certificate-chain, debug, bundle/version, ZIP and packaged-Web-resource checks. Temporary overlays, staged projects and isolated homes are removed on success and failure; a PASS receipt is written only after cleanup and tracked-profile verification. Use absolute paths for `storeFile`, `profile`, and `certpath`, and `SHA256withECDSA` for `signAlg`.

The L27-B entry and its synthetic failure/cleanup tests are connected and make the `harmony-release-build-entry` preflight check `READY`. No real signing material has been supplied and no signed HAP has been produced or accepted. The entry assembles a module HAP; Huawei channel `.app` packaging, device testing, store submission and store acceptance remain open.

The JavaScript verification harness transpiles the proxy source with TypeScript and exercises it against API-shaped mocks; it is not native hardware or device acceptance. Store submission and release acceptance are not included.
