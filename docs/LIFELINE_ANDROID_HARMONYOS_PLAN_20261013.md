## 1. 推荐决策

采用“一套现有游戏核心、两个平台工程”的路线：Android 使用 Capacitor 承载本地 Web 资源，原生 HarmonyOS 使用 ArkTS/ArkUI + ArkWeb 承载同一份资源，通过很薄的平台接口处理存档、分享、生命周期和渠道服务。继续复用 FastAPI/WebSocket 后端。先用双平台真机原型验证关键能力，再投入完整适配。

这是一项原生安装包中的混合应用方案；鸿蒙工程和系统功能使用原生能力，游戏主界面暂由 ArkWeb 绘制，不能把它描述为已经全部用 ArkUI 重写。鸿蒙是否需要扩大原生界面范围，以性能、交互和目标渠道审核结果决定。

| 目标 | 工程与发布形式 | 首版覆盖 |
| --- | --- | --- |
| Android 手机 | Capacitor + 少量 Kotlin 原生适配；签名 APK，渠道需要时再产出 AAB | 国内 Android 设备，以及实际支持 Android 应用的华为设备 |
| 原生 HarmonyOS 手机 | DevEco Studio、ArkTS/ArkUI、ArkWeb；HAP 用于开发调测，App Pack `.app` 用于提交市场 | 独立安装、签名、渠道接入和真机验收 |
| 网页 | 保持现有 Vue/Canvas 页面和共享游戏模块 | 与移动端棋谱、规则及联机协议保持兼容 |

Capacitor 官方明确支持加入既有 Web 项目，正式支持目标列为 Android、iOS 和 Web；本计划不把它视为现成的原生 HarmonyOS 运行时。[Capacitor 安装要求](https://capacitorjs.com/docs/getting-started)、[支持目标](https://capacitorjs.com/docs/getting-started/environment-setup)。鸿蒙上架包与 HAP 的区别见[官方应用程序包术语](https://developer.huawei.com/consumer/cn/doc/doccenter-getting-started/application-package-glossary)。

首版保留“教学 → 对局 → 结算 → 保存/复盘 → 分享棋谱”的完整体验，并保持网页与移动端互通。免费、不接广告和支付 SDK；只保留未来可扩展的接口边界。

## 4. 软件结构与关键实现

共享游戏层保持 JavaScript；只有平台接口分实现，避免同时维护三套规则或给整套 UI 换框架。建议结构如下，路径均为待新增，不代表已实现：

```text
web/web前端/                      共享规则、AI、Canvas、教学、棋谱和业务 UI
web/web前端/platform/             browser / android / harmony 能力适配
mobile/package.json              移动构建入口与锁定依赖
mobile/tools/                    固定资源构建、校验与打包脚本
mobile/android/                  Capacitor Android 工程与渠道插件
mobile/harmony/                  ArkTS/ArkUI、ArkWeb 和渠道服务
mobile/config/                   非敏感的环境与渠道配置
mobile/tests/                    平台契约、真机用例与恢复验证入口
docs/verification/mobile-*/       紧凑清单、哈希和验收收据
```

构建产物、签名私钥、证书密码、原始截图日志及安装包留在本地受控目录或受控发布存储。源码、锁文件、必要配置、测试与紧凑收据进入版本控制；二进制模型继续遵守仓库的发布资产政策，以清单/哈希定位，不放入普通 Git 历史。

### 4.1 本地资源和构建

- 先增加确定性的资源收集/构建流程，固定 Vue、字体和必要数学排版库；记录许可。后续确有收益再引入更复杂的打包转换。
- 为 Web、Android、HarmonyOS 生成资源清单，维持一致的游戏核心版本；统一处理现有 `?v=` 缓存版本、动态 import、Worker 脚本、指南和 F32 二进制路径。
- Android 采用 Capacitor 的本地资源服务，验证安全上下文；若改用定制 Kotlin WebView，再采用官方 `WebViewAssetLoader`，不默认要求同时维护两种容器。
- 鸿蒙使用 ArkWeb 本地资源映射。重点验证安全的 HTTP(S) 来源、资源拦截、正确 MIME、模块 Worker 的子请求、fetch 与 `crypto.subtle`，不能只证明首页 HTML 能打开。
- 只对白名单路径和来源开放本地映射与原生桥，外链在系统浏览器打开。禁止通过关闭 Web 安全、跳过模型哈希或开放任意文件访问解决兼容问题。

依据：Android 官方建议用 WebViewAssetLoader 解决本地内容的同源加载；鸿蒙官方列出了 file/resource 跨域、DOM 存储及资源拦截问题。[Android 本地内容](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)、[ArkWeb 加载问题](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/web-page-loading)。具体组合仍须真机验证。

### 4.2 平台接口

平台接口限定为：能力查询、保存/读取、文件导入/分享、返回事件、前后台事件、网络状态、震动（可关闭）、渠道登录与实名状态。Web 使用现有浏览器实现，Android/HarmonyOS 分别接原生实现。广告和支付暂不装 SDK。

桥接使用固定方法名、版本、请求 ID、输入长度与结构验证、超时及错误返回；禁止暴露任意代码执行、任意文件路径和任意网络代理。原生登录凭据使用平台安全存储，服务端保持最终鉴权。需要游戏中心 SDK 的渠道通过适配层接入，普通不联网功能不依赖 Google 服务。

### 4.3 存档、触控与进程恢复

- 每步先构造带 schema/rulesVersion/revision 的可恢复记录，写入成功才标记“已保存”；保留上一份有效记录和迁移前备份，损坏记录隔离。不要只在退后台回调中保存。
- 复用设置 + 完整动作序列重放；如增加快照，须保存并验证 Superko 历史、逻辑边、跳过/认输、当前玩家和终局。存储适配异步化后要防止较旧写入覆盖较新局面。
- 进入后台停止 AI 与动画，取消未完成请求并增加会话代际；恢复时校验局面，再启动一个 Worker。棋局不能多落一步，AI 对战仍应保持用户的暂停状态。
- 系统返回键优先关闭弹层/复盘，其次回到页面；离开进行中对局给出明确提示。处理刘海、底部手势区、键盘、旋转和 WebView 重建。
- 当前落子由 touchstart 触发。先检查误触，再实现点击/拖动区分；15 边长密集棋盘需要评估缩放/拖动或落点预览，不能用放大按钮代替棋盘命中精度验证。
- 浏览器和安装版的 localStorage 不共享。首版以现有棋谱导出/导入迁移历史对局，不承诺安装后自动继承浏览器存档。

### 4.4 联机和 AI

- 显式提供 release/staging 的 HTTPS API 与 WSS 配置；生产包不显示调试服务器切换。更新登录、房间、贡献上传和错误提示，确保没有请求落到容器的 localhost。
- 检查移动来源的 CORS 与 WebSocket Origin、登录过期和会话恢复；日志不记录完整令牌。网络切换后以服务器动作序列重放校准，避免重复提交和双重落子；房间已过期时明确结束恢复，不假装继续联机。
- 在三端以相同规则版本、动作序列和协议测试互通；后端升级兼容现有网页与前一版 App，不要求所有用户同步升级。
- AI 优先保持现有 Worker 与状态协议，记录每种设备上的时延、内存和热稳定性。任何降低搜索预算的设置都作为可见档位，不静默降低现有同名档位。
- 保留模型来源、seed、SHA-256 和适用人数/尺寸。研究模型必须按 App 运行时验证 hash；当前 ModelFreeAI 在无 `crypto.subtle` 时可能略过摘要比较，也要纳入移动适配，禁止依靠该分支过关。
- 研究 Python/Web 已有终局计分差异记录，见 `docs/WEB_SIZE_TRANSFER_V1_20261012.md`；迁移保持 Web 规则权威，不修改冻结训练协议，不宣称全规则等价或最强模型。

| P1 双平台技术原型 | 3–5 日 | Android 与原生鸿蒙分别装机；验证本地 Canvas、module Worker、资源 fetch、SHA-256、存储、WSS 与文件选择/分享 | 两端各一份真实安装与核心闭环记录；关键能力没有未处置失败 |
| P2 共享移动基础 | 4–6 日 | 包内依赖、固定资源构建、平台接口、API 地址、异步存档与恢复协议、贡献同意 | 飞行模式技术运行、保存恢复与三端协议回归通过；网页原有流程保持可用 |
| P3 Android 完整适配 | 4–6 日 | 系统返回/手势、分享导入、进程回收、签名与安装升级、首批渠道接口 | 真实 Android 设备上完整对局、教学、复盘、恢复与升级通过 |
| P4 原生鸿蒙完整适配 | 5–8 日 | ArkWeb 资源与桥、UIAbility 生命周期、ArkUI 系统页面、文件服务、签名与 APP 打包 | 原生 HarmonyOS 真机同样闭环通过；没有把 APK 兼容运行当作本阶段完成 |
| P5 发行功能与渠道联调 | 5–8 日 | 登录绑定、实名/防沉迷、隐私与注销、备案展示、渠道构建差异和商店材料 | 每个渠道有可提审候选与材料清单；依赖资质的实接已验证或明确阻塞 |
| P6 真机回归与候选冻结 | 5–8 日 | 设备矩阵、异常恢复、互通、性能、长局、升级和安装包资源核验 | 全部发布阻断项通过；证据绑定候选包、源码、规则与设备版本 |
| P7 提审与首发操作 | 2–4 日操作时间 | 按渠道提审、反馈修正、商店可见性与下载安装核验；建立问题处理记录 | 商店审核通过且实际下载安装验证完成；仅上传成功不算上线 |

P5 的资质准备从 P0 同时启动；表中工期是开发/联调占用，不表示外部手续只需 5–8 天。渠道新增 SDK、缺真机或 P1 发现 ArkWeb 不兼容，都需要另计。首个 1–2 周应产出双平台技术证据和实际资质缺口，而不是只有两份打开网页的空壳。

## 7. P1 的决策门：验证失败时如何调整

| 发现 | 先采取的措施 | 对排期的影响 |
| --- | --- | --- |
| ArkWeb 本地模块/Worker 请求失败 | 修正同源映射、MIME、子资源处理；比较实际 SDK/内核版本 | 限时验证；不能用关闭安全或联网加载全站冒充离线成功 |
| Canvas 与规则可用，但后台任务能力不满足 | 单独验证原生 Worker/计算服务适配，保持原有状态协议与固定局面一致 | 追加原型后重新估算，不直接假设 JS 可无修改编译为 ArkTS |
| 手势或局部页面不合适 | 优先原生化设置、账号和系统导航等局部页面；棋盘与规则仍共享 | 局部增加工作，不自动重写全部游戏 |
| 真机性能持续不达标 | 先定位规则、渲染、AI 哪部分耗时；再决定局部原生计算或更明确的 AI 档位 | 若涉及核心迁移，重新评审方案和工期 |
| 渠道要求本方案未覆盖的形态或服务 | 准备可审查原型、资料和渠道问题清单，由用户/发行方获取具体结论 | 审核通过不能由“技术上可运行”推出；新增要求显式入计划 |

备选方案比较：纯 Kotlin + ArkUI 双端重写会增加两套渲染/交互和规则一致性成本；Flutter、Unity、Cocos 等迁移会引入新的渲染与工具链，现有 Vue/Canvas 的直接复用有限；PWA 可继续作为网页能力，但不能完成原生鸿蒙商店发行目标。只有原型提供了具体反证，才升级为这类较大迁移。

## 8. 发布验收矩阵

下列均是计划门槛，当前移动状态全部为 `NOT-RUN`。性能阈值是建议目标，P1 在固定设备、棋盘尺寸和 AI 档位上测量后冻结。

| 验收项 | 标准与证据 |
| --- | --- |
| 三端规则一致 | 同一棋谱在 Web、Android、HarmonyOS 重放；每步比较合法性、节点、逻辑边、历史、行动方、跳过/认输、终局、离散面积与赢家。覆盖 v1 导入、v2 新局、5/9/15 尺寸及实际支持的人数组合 |
| 首屏与离线资源 | 干净安装、清缓存后断网；无需 CDN 加载即可进入允许的本地页面；规则与教学资源完整。正式游玩入口遵守冻结的实名策略 |
| AI 与异步 | 新局、取消、切后台、Worker 崩溃、模型损坏/缺失后不接收旧结果、不落非法步；降级可见；研究型号和普通 AI 分别记录 |
| 持久化 | 操作后立即回收进程、写入中断、低存储、损坏导入、旧存档升级分别验证；至少保留最近一次明确成功保存的局面，不把存储失败展示为已保存 |
| 联机互通 | 三端组合；弱网、Wi-Fi/移动网切换、登录过期、重复动作、重连和房间过期；没有双重落子或跨房间污染 |
| 操作体验 | 360/390/430 等逻辑宽度、真实触摸、系统大字体、导航键/手势、旋转、键盘；主要按钮不小于约 44–48 逻辑像素；密集棋盘落点可辨认和确认 |
| 性能 | 建议中档机冷启动可操作中位数 ≤3 秒（至少 10 次）；非 AI 输入反馈 p95 ≤100ms（固定场景 ≥100 次）；快速 AI 档目标 p95 ≤2 秒，15 边长与深档另列；后台不持续搜索 |
| 稳定性 | 核心设备各做不少于 30 分钟混合使用、完整对局和反复恢复；无数据损坏、无法继续对局或持续恶化的内存/发热问题。样本通过不宣称全设备零崩溃 |
| 权限与数据 | 不同意贡献时零棋谱上传；撤回后停止队列；拒绝非必要权限不损坏基本功能；校验 SDK 初始化时机、注销及隐私披露 |
| 安装升级 | 新装、覆盖升级和数据迁移；正确签名、版本号单调递增；无调试配置/私钥入包；资源与模型哈希齐全 |
| 商店完成 | 对应渠道的资质、SDK 和审查意见闭环；实际商店页面与最终安装包一致，下载安装后再验核心路径 |

最低设备集建议为：Android 中档机、较低性能/最低支持版本机、支持 Android 包的华为设备，以及两档原生 HarmonyOS 真机；若首版声明支持平板/折叠屏，再加入相应设备。可借用或使用官方设备服务，但模拟器和桌面浏览器不能覆盖真机触摸、功耗与系统回收。

最低 Android/HarmonyOS 版本暂不凭经验写死。在 P0/P1 根据当期 Capacitor、WebView/ArkWeb、渠道 SDK 支持范围与实际设备确定 min/target/compile SDK，并把工具链版本写入构建说明。

## 9. 发布与持续维护

- 复用适合的干净 `codex/` 分支/工作树，从冻结候选起步；不清理或整包提交当前已有工作。共享代码修改和两个平台工程分别组织小提交，推送前按 AGENTS.md 审阅、检测秘密/大文件和验证。
- 基本流程固定为：共享资源构建 → 规则/协议回归 → 双平台构建 → 真机候选验证 → 签名包与哈希 → 渠道提审。CI 保存来源与紧凑结果，签名由受控环境提供。
- 首版代码更新走应用市场版本发布；不依赖远程替换整站作为主要更新方式。服务器保存与前一版移动协议兼容能力，Web 和 App 可以异步升级。
- Web 静态资源有既有回滚机制；移动商店版本通常不能直接降级覆盖。移动端出现问题时停止继续分发、恢复兼容服务，并用更高版本号发布修复；存档迁移保留恢复材料。
- 记录用户反馈、崩溃与 ANR 的渠道报告、模型加载失败和恢复失败等必要信息；新增遥测需同时更新数据说明，不采集原始账号、完整令牌或默认上传棋谱。
- 稳定发布后再评估付费/广告：渠道支付、权益验证、退款/恢复购买、广告同意与未成年人策略均另行设计和提审，不把后来加入 SDK 当成普通文案更新。

## 10. 开工顺序与尚待确认的信息

推荐下一项具体开发任务是 P0 + P1：先冻结一份正确的网页发布基线，补齐最小离线资源，然后让 Android 和原生鸿蒙各自在真实设备上完成“开局 → AI 落子 → 保存 → 回收进程 → 恢复 → 导出棋谱”。同时由用户/发行负责人确认主体、版权、出版审批、APP 备案和渠道要求。
