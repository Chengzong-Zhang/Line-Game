# LIFELINE Lab：个人项目建设计划

制定日期：2026-09-21。状态：执行中；本文件仍是产品与工程计划，不等同于发布通过证明。

## 1. 项目定位与成功标准

**LIFELINE Lab（生命线实验室）：一款可以对战、复盘和探索 AI 决策的原创策略游戏。**

玩家通过扩张、围地和切断连接参与博弈；对 AI 感兴趣的人可以沿着一盘真实对局，进一步查看连接结构、合法走法、历史限制和搜索候选。研究报告承担其中一个明确问题的论证。

首页建议文案：

> 连成领土，切断对手的生命线。与 AI 对战，回看关键一步，探索每一步背后的规则。

英文短介绍：

> Play an original strategy game, revisit critical moves, and explore the rules and decisions behind game AI.

优秀个人项目的验收维度：

| 维度 | 需要交付的证据 |
|---|---|
| 真实体验 | 陌生人能独立学会基本操作、完成对局、打开复盘；保留实际试用反馈 |
| 项目辨识度 | 切断机制有直观演示；同一盘棋能进入规则和 AI 分析视图 |
| 技术深度 | 规则引擎、异步搜索、完整历史回放、版本契约和验证样例可检查 |
| 工程完整性 | 可复现启动、关键回归、错误恢复、部署回滚与简洁文档 |
| 个人表达 | 展示设计取舍、个人负责内容、AI 辅助开发方式、真实缺陷与修复过程 |

v1.0 的核心演示闭环：**打开网站 → 交互教学 → 和 AI 下一局 → 看懂结果 → 回放关键一步 → 打开该步的规则解释 → 导出棋谱。**

## 2. 当前资产与待确认项

本次依据仓库 README、前端入口、GameEngine、GameController、AIStateProtocol、研究目录和现有测试入口做静态核对；未进行线上完整交互测试，也未重新运行历史实验验证。

| 资产 | 当前证据 | 计划处理 |
|---|---|---|
| 原创规则与 Web 引擎 | 节点、逻辑边、切断、领土、Superko、跳过、认输已有实现 | 作为产品基础，补面向玩家的解释 |
| 本地双人/三人 | README 与控制器有对应能力 | 保留；新手默认从双人小棋盘开始 |
| 搜索 AI 与提示 | 当前检出有 AIEngine/AIWorker、深度 2/3/4、提示 Worker | 先校准速度和难度，再完善解释 |
| 神经网络 AI | 2026-09-10 历史部署记录存在 Topology-GNN + PUCT；当前检出未见对应前端模块 | M0 核对线上、Git 与模型版本，确认后决定恢复集成或延期 |
| 联机 | 账号、房间、动作同步、断线恢复及相关测试已有入口 | 先回归休闲联机；主闭环先使用本地 AI |
| 规则教学内容 | GuideContent 与 Markdown 图文说明已有内容 | 转化为可操作小关卡，复用素材 |
| 回放基础 | 控制器有 replayBatch/房间恢复；状态协议包含 historyHashes 等 | 新增用户可见棋谱协议和复盘页；恢复内部接口不等于完整复盘产品 |
| 研究证据 | AAAI 内容稿记录 side-5 枚举、side-6 历史合法性 witness、有限基线比较 | 选少量样例做实验室展品，逐项检查规则与验证程序 |
| 验证基础 | 领土、AI 控制流、提示、联机恢复、反例测试脚本已存在 | 纳入对应模块的自动检查 |
| 运行与发布 | Web 依赖 CDN；根文档以 Minimax 为主；启动错误中仍有 TriAxis 名称 | 固定运行依赖，统一品牌与实际能力说明 |

关键版本边界：Web 页面默认 territory-v2；裸 GameEngine 默认 v1；Python/Pygame 是 legacy v1 lineage；研究结果依各自冻结协议。旧模型、旧棋谱与研究样例都需要明确对应的规则版本。

## 3. 用户与信息架构

首要用户：愿意花 5–10 分钟尝试新策略游戏的人。第二类用户：对搜索、RL 或 GNN 感兴趣的同学。第三类用户：查看作品集的导师、面试官和开发者。

桌面端建议四个入口，手机端保持同样语义：

| 入口 | 用户要完成的事 | 首版范围 |
|---|---|---|
| 玩一局 Play | 学会玩法、挑战 AI、邀请朋友 | 引导、本地 AI、既有休闲联机入口 |
| 复盘 Replay | 回看、理解、保存一盘棋 | 时间轴、逐步播放、关键事件、导入导出 |
| 实验室 Lab | 理解规则与 AI | 当前对局检查器、精选反例、候选走法 |
| 项目 About | 了解实现、运行代码、阅读研究 | 项目故事、架构、演示、GitHub、技术报告 |

常规对局只显示轮到谁、比分、上一步、提示和必要操作。节点、逻辑边、历史集合、搜索预算与模型版本在复盘/实验室按需展开。中英文沿用现有能力，新增核心流程同步维护。

## 4. v0.1：第一次玩就能理解

### 4.1 交互教学

设计四个短场景：连接扩张、闭合围地、切断与断联清除、结算。保护区与三点限制在相关操作时给出说明；Superko 放进进阶示例。

每关只要求一个动作。用户先操作，随后看到高亮和解释；可跳过、重玩。关卡由固定配置和动作序列驱动，使用真实规则引擎验证。

目标：约 3 分钟理解基本玩法。教学完成后直接进入适合新手的双人小棋盘；默认尺寸由试用确定，候选为现有支持的小尺寸，不直接认定越小越容易。

### 4.2 棋盘反馈

- 点击节点时明确显示选中位置；手机密集棋盘可使用预选后确认，避免精度问题。
- 切断时先强调被切边，再显示清除节点；动画支持关闭或减少动态效果。
- 非法动作返回人能看懂的原因，并高亮对应位置；检验失败不修改棋局。
- 正式比分沿用规则引擎的离散 area，计算中显示状态，结算显示获胜依据。
- AI 思考中有状态和中止入口；重开、切换设置后旧 Worker 结果不得落子。
- AI 超时或载入失败时保留棋局，提供重试或明确告知的搜索 AI 降级。

### 4.3 单人可靠性

每次确认行动后自动保存本地对局；刷新可恢复。保存包含规则版本和必要历史信息；存储失败要有提示。首局不要求注册。悔棋仅在本地练习开放，并恢复相应历史、跳过状态和 AI 回合。

**v0.1 完成条件：新人能走完教学、和 AI 完成一局、解释输赢；手机可操作；刷新恢复可用。**

## 5. v0.2：把一盘棋变成可理解的过程

### 5.1 棋谱与复盘

定义版本化棋谱：schemaVersion、rulesVersion、引擎构建标识、棋盘/玩家配置、初始状态或合法历史前缀、带序号的行动、终局摘要；AI 元信息可选。派生事件可以缓存，回放时由规则重新计算。

MVP 优先 JSON 文件导入导出，不依赖云端棋谱服务。公开分享链接后续按实际需求做，不能让大历史塞入 URL。导入文件按数据解析，校验大小、结构、版本、行动顺序与合法性；失败不得破坏当前棋局。

复盘支持首步、上一步、下一步、自动播放和时间轴定位。完整历史由起点重放构建；长棋谱的检查点必须保留 Superko 所需历史。保留落子、跳过、认输的语义，自动跳过不得重复执行。

关键事件第一版采用确定规则：切断、较大规模断联清除、领土变化、终局。文案使用“发生了什么”；没有充分搜索依据时，不称为“最佳一步”或“致胜点”。

### 5.2 局面检查器

同一棋盘支持叠加显示节点占用、逻辑边、连通分量、合法落点和领土。点击候选落点可查看合法性判断；对于 Superko，只有拥有可重建的前序棋谱时才展示对应历史局面。

检查器使用只读快照或隔离副本，不得因试探动作改变真实对局。无合法来源的手工编辑局面标为沙盒，不能冒充可达状态。

### 5.3 三个精选展品

1. 切断连锁反应：展示一条边变化如何导致节点与领土变化。
2. 历史与合法性：从已验证 witness 中选择案例；精确写出“两段历史下哪个表示相同、哪个动作合法性不同”，显示必要的当前玩家等条件。
3. AI 的候选比较：固定局面下切换搜索预算，查看实际候选、用时和估值变化。

研究 witness 先验证再接入。若其规则仅适用于研究版本，使用明确标注的只读研究展示；不能把研究 v1 witness 直接贴到 Web v2 对局中。side-5 未发现某类混淆的枚举结果可以保留为结论边界。

**v0.2 完成条件：用户能导出一局、重新导入并逐步回到相同终局；能从真实回放进入检查器；至少一个验证过的机制案例可操作。**

## 6. v1.0：AI 深度、作品展示与正式发布

### 6.1 AI 体验与 AI 竞技场

普通玩家看到经试用校准的难度和预计思考时间；深度 2/3/4 属于同一搜索算法的配置。神经网络 AI 作为可选能力，需确认模型来源、规则兼容、浏览器推理与性能后开放。

第一版 AI 对比包含：一个简单参考策略、现有搜索 AI；已验证兼容时加入一个神经网络 AI。研究目录里的所有方法无需一次搬上网页。

竞技场先使用离线计算好的固定对局，浏览器负责播放与展示。访客可运行少量限时 AI 对战；长评估由维护者启动，必须有预算和中止入口。

AI 解释以实际计算字段为准：Minimax 的启发式分量/候选/搜索深度；PUCT 的访问次数、策略概率和估值。估值未经校准不得显示为真实胜率；无充分搜索时不标“最优”。

对比结果至少注明规则版本、棋盘尺寸、先后手、对手、模型版本、搜索预算、实际用时和样本数。相同时间预算的体验比较与相同搜索次数的机制比较分别陈述。重复确定轨迹不能算成独立重复试验。

### 6.2 视觉与访问体验

围绕三角网格、领土和切断建立统一视觉语言：清晰的棋盘、克制的配色、统一图标与面板。颜色外增加节点形状/轮廓与当前玩家标识，支持键盘焦点、可见状态提示、减少动态效果。

先覆盖桌面与手机竖屏，检查窄屏没有关键按钮溢出。模型、公式渲染和实验室代码按需加载；核心游戏运行依赖固定版本并随发布提供，避免首次游戏依赖不稳定的外部 CDN。

### 6.3 作品集交付

- README：一句话介绍、真实运行截图/短演示、在线入口、快速启动、核心特色、架构和能力边界。
- 90 秒演示：15 秒规则 → 25 秒对战与切断 → 25 秒复盘/检查器 → 15 秒 AI → 10 秒代码和报告入口。
- 项目案例文章：动机、三次关键取舍、一个真实失败与修复、试用反馈、下一步。
- 技术说明：状态为何需要历史、Worker 过期结果处理、回放版本化、模型与规则的兼容要求。
- 发布页：版本说明、已知问题、验证摘要、启动方式；大模型文件通过合适的发布渠道提供。
- 贡献与素材说明：代码/模型/图片来源、AI 辅助开发边界、许可待作者确定后补齐。

简历表述骨架，完成后用实测数据填写：

> 设计并开发 LIFELINE 策略游戏与 AI 实验室，实现版本化规则引擎、浏览器异步搜索、棋谱复盘及状态可视化；根据用户试用改进教学与移动端交互，并提供可复现的机制验证与技术报告。

## 7. 技术方案与依赖

沿用当前 Vue/Canvas、JavaScript 引擎和 Python 联机后端，按功能增量演进。核心依赖如下：

```text
版本盘点与规则契约
  ├─ Play：教学、反馈、AI 对战、恢复
  └─ 棋谱协议 → Replay → 局面检查器 → 精选机制案例
AI 来源与兼容核对 → AI 适配器 → 候选解释 / 竞技场
以上可用成果 → 用户试用 → 修正 → 展示材料与发布
```

建议新增的职责模块（具体文件名由实施时按项目约定确定）：

| 模块 | 责任 | 首要验证 |
|---|---|---|
| GameSession | 对局配置、动作提交、自动保存、恢复 | 刷新、悔棋、跳过、认输完整性 |
| ReplayCodec / ReplayController | 棋谱校验、序列重放、时间轴 | 逐步重放一致、损坏文件隔离、未知版本提示 |
| TutorialRunner | 关卡条件、引导动作、完成状态 | 每关目标可达、教学动作符合规则 |
| Inspector | 只读局面诊断与说明 | 不污染原状态、合法性与引擎一致 |
| AIAdapter | 统一请求/取消/候选/预算接口 | 过期响应、超时、规则不兼容、载入失败 |

将 OnlineApp 的相关业务逐步移入模块，避免一次性重写。重用现有状态协议，但 Worker 快照与公开棋谱职责不同，需独立定义长期兼容格式。

现有后端负责动作转发，不具有完整规则裁决能力。因此公开竞争排行与防作弊联机不进入首版；未来若做排位，需独立设计服务端裁决与一致性验证。休闲联机仍应验证重连、动作顺序、重置和离房恢复。

## 8. 排期、优先级与切割线

按单人约 120–170 小时有效工作量估计；每周 12–15 小时约 8–14 周。学习成本、AI 集成和用户招募可能扩大工期。以下是工作包估算，不是完成承诺；M0 后更新。

| 阶段 | 工时估计 | 交付物 | 通过条件 |
|---|---:|---|---|
| M0 基线确认 | 8–12h | 线上/仓库/规则/模型清单；核心流程基线；优先缺陷表 | 每个对外能力有当前证据，首版配置确定 |
| M1 上手体验 | 24–32h | 教学、棋盘反馈、AI 状态、自动保存 | 形成 v0.1；约 3 名新人第一轮试用并记录问题 |
| M2 复盘 | 24–32h | 棋谱协议、导入导出、时间轴、关键事件 | 完整历史可重放；异常导入安全失败 |
| M3 实验室 | 20–28h | 当前对局检查器、精选案例、候选解释 | 形成 v0.2；机制可操作且与真实引擎一致 |
| M4 AI 与发布质量 | 24–36h | AI 校准/兼容检查、可选模型、性能与端到端回归 | 核心闭环稳定；重故障无未解决项 |
| M5 作品集与试用修正 | 20–30h | README、演示、案例文章、技术报告初稿、发布候选 | 累计约 8–12 名真实试用者，有修正记录与交付材料 |

M4 的依赖固定和启动稳定性若影响首局，提前到 M1。神经网络 AI 若超过约 12 小时仍无法完成可信兼容集成，单独延期，先交付搜索 AI。研究版 witness 接入若阻塞，先交付 v2 下可验证的切断展品和检查器。

P0：首局、规则反馈、可靠 AI、保存恢复、完整复盘、一个检查器案例、可运行文档。

P1：更多机制展品、候选比较、神经网络 AI、精选对战结果、分享链接。

P2：云端棋谱库、公开排位、三人神经网络 AI、用户自定义规则、通用多游戏框架、移动原生 App、在线训练。

若工期压缩，按 P2 → P1 的顺序缩减；优先保留端到端体验、规则正确性和移动端可用性。

## 9. 用户验证与发布验收

小样本试用用于发现体验问题，不用于证明人群统计结论。第一轮约 3 名完全不了解规则的人；第二轮补 5–9 人，尽量包含手机用户和少量懂 AI 的同学。由作者招募，本计划不代表已邀请或已有用户。

每位试用者执行五项任务：不听口头指导完成教学；下一局；说明胜负；找到一次切断的回放；导出并恢复棋谱。记录耗时、卡住的位置、求助次数、误操作、是否愿意再玩，以及具体原因。

初始发布目标如下，均需测量，尚未达成：

| 指标 | 初始验收目标 | 测量方式 |
|---|---|---|
| 教学可理解性 | 首轮 3 人至少 2 人无口头救场完成；失败则修正后再测 | 逐人观察记录，保留分母 |
| 完整体验 | 最终试用约 8–12 人中至少 80% 能独立完成核心任务 | 报原始人数与失败点；明确不是统计推广 |
| 首次加载 | 声明设备与网络条件下，核心游戏可操作时间中位数 ≤3 秒 | 冷缓存至少 5 次；模型与公式不阻塞首屏 |
| 操作反馈 | 标准测试棋盘与密集局面中，确认输入的反馈 p95 ≤100ms | 记录设备、局面集合和采样数；规则计算可异步 |
| AI 等待 | 快速档多数落子 ≤2 秒；较深档提供可见预算并允许中止 | 实际搜索用时与取消用时分别记录 |
| 回放一致性 | 固定棋谱集全部重放到相同完整规则状态与终局分数 | 包含 Superko、连续跳过、认输和版本差异 |
| 故障恢复 | AI 超时、刷新、损坏棋谱、重开后迟到响应有明确处理 | 自动边界用例 + 人工端到端检查 |

规则状态比较不强求缓存或 positionRevision 等实现计数相同；比较棋盘、边、行动方、历史、跳过、认输与终局等决定规则的字段。

评估棋盘至少覆盖 6、9、15 与非首步密集局面；小棋盘是默认体验，较大棋盘可标为高级。若大棋盘达不到预算，应优化、提示限制或缩小受支持配置，不能静默改变正式规则。

现有回归入口按改动选用：verify-territory-v2、verify-ai-control-flow、verify-hint-worker、verify-online-recovery、verify-territory-worker。新增测试围绕教学关卡有效性、回放完整性、状态诊断无副作用和真实故障恢复。发布检查桌面 Chrome/Edge 与至少一台真实手机浏览器；Safari 若未实测明确列为未覆盖。

v1.0 发布门槛：核心闭环可完成；上述正确性与恢复检查通过；关键试用障碍已修正；文档与发布能力一致；发布包有版本、资源哈希和可回滚路径。观测先用试用笔记和本地性能数据；未来加入线上统计时再明确事件与数据用途。

## 10. 论文与技术报告的位置

报告工作题目：**LIFELINE 中历史依赖合法性的构造、回放与诊断**。

核心问题：在明确定义的观测投影下，两个可达状态能否具有相同观测却对应不同合法动作？如何保存两段轨迹，并让第三方独立重放验证？

报告组织：问题与规则定义 → 完整状态/观测投影 → 样例构造和验证 → 枚举范围与阴性结果 → 对建模和评估的启示 → 限制。已有 CNN/GNN 对比可作为背景或附录，是否放入取决于其与主问题的关联。

游戏完成度与报告学术贡献分别验收。工程质量本身不能证明研究新颖性；没有学习收益实验不自动否定机制或基准研究。后续论文需要补相关工作检索、明确差异和对应证据，再选择合适形式及会议。

首个版本只整理现有证据、少量验证和可视化，不依赖新增大规模训练。未来长期实验遵守仓库既定要求：可恢复检查点、增量完成记录、独立监督、重复工作防护、有限重试、暂停/停止入口，并先测试中断恢复。
